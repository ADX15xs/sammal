## 1. 需求 3 定论：三条插话只响应最后一条 —— 不是投递缺陷，是语义设计缺口

### 证据（会话 `20261104-003832-1800`，`session.jsonl`）

| seq | 事件 | 内容 |
|---|---|---|
| 1648 | `assistant/message` | 300 行回答（len=5254），**先写完** |
| 1649 | `user/message` | 先停一下，第 50 行附近是什么内容？ |
| 1650 | `user/message` | 先停一下，第 100 行附近是什么内容？ |
| 1651 | `user/message` | 先停一下，第 200 行附近是什么内容？ |
| 1652 | `request/header` | `messageCount = 5` = [user, assistant, u50, u100, u200] |
| 1689 | `assistant/message` | 只重列 198-202（len=92），即只回应「200 行附近」 |

### 结论

**三条全部送达模型，零丢弃。** 链路逐行可验：

- TUI `handleKey` busy 分支 `m.deps.Send(text, nil)`（`internal/tui/model.go:201`）
- → `Agent.Submit` 在 `Running()` 时转 `Steering`（`internal/agent/agent.go:252-260`）
- → `inbox chan string` 容量 16（`agent.go:164`），每条独立入箱，无覆盖
- → `absorbInbox` 全量排空（`agent.go:364-376`），**逐条** append 成 3 条 `user/message`
- → 投影逐条保留、不合并（`internal/session/session.go:405-408`）
- → 线序列化 1:1，不合并（`internal/provider/types.go:139-157`）

若有覆盖/丢弃，`messageCount` 必然是 3 而不是 5。

**模型只答最后一条，是「三条连续 user 消息、内容几乎相同、中间无 assistant 回复」被读成
同一指令的重复。** 但要把账算在设计上：吸收时机固定在段末（followUp，不是 steer），
同一批的三条被当成三条并列裸消息交出去，等于把并发语义降级成「用户连发三次改口」。

### 修法（已获批）

`absorbInbox` 整批吸收 → 合并为**一条** user 消息：

- 1 条：原样写入（日志形态、`/resume`、既有测试全不变）
- ≥2 条：带批次抬头 + 序号

```
（生成中插话 3 条，按先后顺序，请逐条纳入处理）
1. 先停一下，第 50 行附近是什么内容？
2. 先停一下，第 100 行附近是什么内容？
3. 先停一下，第 200 行附近是什么内容？
```

代价：日志里出现合成抬头（I1 无损——写什么发什么，重放哈希自洽；`/resume` 照实显示）。

**翻案条件**：合并后模型仍只答最后一条 → 说明问题在「先停一下」这个诉求没被满足，
只能上 T11 真打断。除此之外不改方案。

> 参照：WorkBuddy 官方文档（`workbuddy.cn/docs/workbuddy/Conversation`）的做法是
> 「消息进输入框上方的队列，当前一轮结束后**依次**处理，且每条可编辑/删除/排序」——
> 逐条而非合并。我方合并是为省请求数，用户已接受；不追平它的队列编辑能力。

## 2. 需求 1：思考行不撤（最小改动版）

### 现状与「空洞」的确切成因

- 实时渲染：`streamBlockLines`（`internal/tui/model.go:661-681`）恒定 1 行，
  `dim("- 思考中 12s | <当前行尾部跟随>")`，只在自绘帧里，从不进滚动区。
- 撤行发生在 `ReasonFinalEvent`（`model.go:399-401`，`thinking=false; resetReason()`）
  与 `TextDeltaEvent` 兜底（`model.go:373-378`）。
- 帧高 3（思考 1 + 状态 1 + 输入 1）→ 思考撤走瞬间变 2（此刻答案还没到）→ 答案到达再变 3。
  **这一缩一长就是空洞的来源**：滚动区没有新增内容，帧却先矮了一行。
- 实证：`docs/image/SMOKE/1793561168405.png` 里 `> 请从 1 编号到 300…` 与
  `1. 今天天气真好。` 之间那条空行。

### 改法（R1，推荐）：把「撤走」换成「下沉」，一行对一行

`ReasonFinalEvent` 里，先用 `printScroll` 把**当前正在显示的那一行**落进滚动区，
再撤帧内思考行。滚动区 +1 行、帧 −1 行，净效果 = 该行原地不动，空洞消失。

具体：

1. 落盘文本 = `dim("- 思考 " + 已耗时 + " | " + reasonLine())`（把 `思考中` 改为 `思考`，
   因为此时已结束；正文取当前正在显示的那一行，与用户刚才看到的完全一致）。
2. 正文为空（模型只吐了思考计时、没正文）时**仍然落这一行**：否则帧缩 1 行而上无新增，
   老空洞原样复现。
3. 正文超宽时 `printScroll` 会折行成多行——净插入 ≥ 帧收缩，只会多不会少，不产生空洞。
4. `StreamRestartedEvent`（`model.go:403-412`）**不落盘**：重连作废的思考不该写进滚动区。
5. `MessageFinalEvent` / `TurnEndedEvent` 的 `resetReason()` 不动（此时已处理完）。

### 为什么这是「少改」

- 不累积全文：**不需要动 `Model.reason`**，从而绕开那个雷（见下）。
- 不改 `Transcript()`：`/resume` 长度分毫不动（`internal/session/session.go:602-631` 明确
  「chunk 不参与」）。
- 每次思考结束的落盘增量 = **1 行**，与思考长度无关。

### 必须绕开的实现雷（上一版计划踩的）

`Model.reason` 是**值类型 `strings.Builder`**（`model.go:56`），而 `Model` 全程按值拷贝
（`Update` 返回 `Model`）。`strings.Builder` 写过再被拷贝，后续写入会 panic：
`strings: illegal use of non-zero Builder copied by value`。

现在不炸，只因它**从未被写过**——`appendReason`（`model.go:496-506`）只维护 `reasonCur`，
遇 `\n` 就丢旧行，`m.reason` 恒空（`reasonLine()` 里的 `lastLine(m.reason.String())` 是死兜底）。

本版方案不需要写 `m.reason`，**不要顺手去「修好」它**。若将来要全量落盘，必须先换
`*strings.Builder`（`m.stream` 已是指针，同一个坑前人踩过）。

### 已知副作用（观察项，不判失败、不修）

- `frameHold`（`model.go:620-634`）在排空期间冻帧，思考行可能**短暂重复 1 帧**：
  上面是刚落盘的那行，下面是还没撤掉的同一行。既有机制的既定行为。
- `/resume` 仍不含思考。实时有、回放没有，是刻意的结论视图差异，写进判据防误判回归。

### 兜底（若实机仍见空行）

换 R2：`ReasonFinal` 后**不立刻**缩帧，让该行继续占位，直到第一个 `TextDeltaEvent`
在同一帧槽位被答案首行接管（过渡期帧高恒定 1→1，零落盘）。此时思考正文终将消失，
但「先缩后长」的抖动不存在了。**不回到「整段落盘」。**

### 3.3 顺带还 D4 —— 但先看清现状：**三个去重测试是空转**

> ⚠️ **本节结论已被 `db40684` 推翻**：去重不是「改判保留」，而是整段删除（红队推演见 §0.1）。
> 保留本节的价值在最后一段——「空转测试」是怎么骗过绿勾的，别再写这种断言。

代码顺序是「先 `addInterject` 再 `Send`」（`model.go:200-201`），所以 500ms 内连按两次 Enter：
**模型收两条、屏幕显示一条**。更麻烦的是现有测试根本没验证到这一点：

`TestInterjectDedupeInWindow`（`interject_test.go:79`）第一次 Enter 后没跑 `drainAll`，
`scrollQ.draining` 仍为 true；第二次 Enter 时 `printScroll` 命中
`if !any || m.scrollQ.draining { return nil }`（`scroll.go:277`）返回 nil，
`printedLines(cmd)` 自然是空 —— 测试断言 `len(prints2)==0` **恒成立，与去重无关**。

- 重写 3 个测试为有效断言：每次 Enter 之间 `drainAll`，直接断言
  「第二次既不产生新落盘、也不产生新投递」；再加一个「超过 500ms 可重发」的用例
